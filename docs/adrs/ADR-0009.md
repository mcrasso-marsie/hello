# ADR-0009: Explicit '-' stdin marker sharing the file decode path

## Context

Users need to count piped text. The architecture forbids a second decoding path or newline translation, and no argument must stay a usage error with exit status 2.

## Decision

We will treat the single argument '-' as standard input, read it as raw bytes from sys.stdin.buffer, and decode it through the same UTF-8 decode step used for files, naming the source `<stdin>` in error messages.

## Alternatives Considered

- Read stdin implicitly when no argument is given: rejected, it breaks the exit status 2 usage contract.
- Auto-detect piped input: rejected, behavior depends on the calling environment and conflicts with the usage error.
- Read stdin through sys.stdin text mode: rejected, universal-newline translation would change CR and CRLF line counts.
- Copy stdin to a temporary file: rejected, it adds filesystem writes and error messages would name a temporary path.

## Consequences

### Positive

- Counts are identical for identical bytes from either source.
- Error contracts stay the same, with `<stdin>` in place of a path.
- The convention matches common Unix tools.

### Negative

- A file literally named '-' must be reached through './-'.
- An interactive terminal on stdin waits for end of input, which can look like a hang.
- The invalid UTF-8 message says `file` even for standard input.
