# Discovery Graph: DG-0005
**Graph Type:** opportunity

## Core Issue

wordcount users cannot learn the byte size of their input. The existing counts do not give it for non-ASCII text.

**Impact/Value:** Users who size buffers, uploads or storage could get the byte size from wordcount. They would not need a second tool.

**Discovery Method:** Written feature intent and user notes from the handoff.

## Patterns

### Pattern 1: byte-count-missing

**Applies To:** The wordcount output line for file and standard input  
**Frequency/Recurrence:** Every run on non-ASCII input  
**Severity/Urgency:** Medium  
**Confidence:** High  
**Current State:** The output shows words, characters and lines. Users must use another tool to get the byte size.  

**Evidence Signals:**

- The wordcount output line reports words, characters and lines, but gives no byte size of the input.
- The user wants the byte count shown next to the characters count.
- For non-ASCII text the byte count differs from the character count: 'café' is 4 characters but 5 bytes in UTF-8.
- Users who size buffers, uploads or storage need the byte count of the input.

### Pattern 2: byte-count-input-parity

**Applies To:** wordcount PATH and wordcount -  
**Frequency/Recurrence:** Every run that reads standard input  
**Severity/Urgency:** Medium  
**Confidence:** High  
**Current State:** File and standard input already give identical three-field output for the same bytes. No byte field exists on either path.  

**Evidence Signals:**

- The byte count must be available for input read from a file and from standard input through '-'.

## Pattern Dependency Graph

The byte-count-input-parity pattern depends on byte-count-missing. Parity only matters once a byte count exists. Both patterns build on the existing file and standard input paths from SPEC-0004.
