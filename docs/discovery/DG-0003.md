# Discovery Graph: DG-0003
**Graph Type:** opportunity

## Core Issue

Users of the wordcount CLI can see the word and visible-character counts of a file but cannot see how many lines it contains, so they have to use a separate tool to get it.

**Impact/Value:** Users get a complete count of a file (words, characters, lines) from one invocation. The line count uses a clearly defined, Unicode-aware boundary rule instead of leaving it to whatever tool they would otherwise use.

**Discovery Method:** Written feature intent from the project owner, refined through one clarification round. In that round the human fixed the line-boundary rule, the whitespace-only behaviour, the output format and the invocation.

## Patterns

### Pattern 1: line-count-missing

**Applies To:** The `wordcount PATH` command's successful stdout output line  
**Frequency/Recurrence:** Every successful invocation of the command  
**Severity/Urgency:** Moderate: a feature gap, not a defect. Existing output keeps working, but its format will change.  
**Confidence:** High: the output format and always-on behaviour were confirmed explicitly by the human.  
**Current State:** The command prints exactly `words: <N> characters: <M>` and gives no line information. Users must count lines with another tool.  

**Evidence Signals:**

- The wordcount command reports the number of words and visible characters in the input file, but not how many lines it has; users want the line count too.
- The line count is always printed: no new flag or option, and the single positional PATH invocation stays as it is.
- Every successful run of `wordcount PATH` should print the line count on the same stdout line, in the form `words: <N> characters: <M> lines: <L>`.

### Pattern 2: line-boundary-definition

**Applies To:** How lines are counted in any decoded UTF-8 input file, including empty, whitespace-only, CRLF and Unicode-separator files  
**Frequency/Recurrence:** Applies to every file. The edge cases (unterminated final segment, CRLF, U+2028, form feed, lone CR) show up whenever files come from mixed platforms or contain Unicode text.  
**Severity/Urgency:** High for correctness: an ambiguous rule would produce counts that users and tests disagree on.  
**Confidence:** High: the human answered each boundary question and explicitly confirmed that the rule is broader than `wc -l`.  
**Current State:** No line-counting rule exists in the project yet. The rule is now defined only in the clarified requirements.  

**Evidence Signals:**

- A line is a terminated segment: every boundary that Python's str.splitlines() recognises counts as a line terminator (including lone CR, U+2028 and form feed), CRLF counts as one terminator, and an unterminated final segment is not counted.
- A file containing 'a', LF, 'b' reports 1 line, because the final 'b' has no terminator.
- A whitespace-only file such as LF LF reports 2 lines, even though it reports 0 words and 0 characters.
- A file containing 'a', CR, LF reports 1 line: CRLF is a single line break, not two.

## Pattern Dependency Graph

The missing line count is the core opportunity. The line-boundary definition determines what number appears in the new `lines: <L>` field, so the output-format change depends on that rule being settled. The rule is independent of the existing word and character rules, which stay unchanged.
