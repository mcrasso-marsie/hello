# Discovery Graph: DG-0006
**Graph Type:** opportunity

## Core Issue

The wordcount output does not report how many words the longest line holds, so users cannot see line length in words.

**Impact/Value:** Users get a longest-line figure without extra tools. The value is convenience only, with no failure to fix. Existing parsers must keep working.

**Discovery Method:** Owner feature intent, the existing SPEC-0001 to SPEC-0005, and the human answers to three clarification questions.

## Patterns

### Pattern 1: longest-line-metric-missing

**Applies To:** The wordcount CLI output for files and standard input.  
**Frequency/Recurrence:** Every run of wordcount.  
**Severity/Urgency:** Low. This is an enhancement, not a defect.  
**Confidence:** High. The owner stated the need and answered the open questions.  
**Current State:** The output shows words, characters and lines. It shows no longest-line figure.  

**Evidence Signals:**

- The owner wants the longest line, measured in words, added to the wordcount output.
- The output today reports `words: N characters: N lines: N` and has no longest-line figure.
- The new field reports a single number. It has no line number and no line text.

### Pattern 2: final-segment-line-rule-mismatch

**Applies To:** The longest-line measure and the existing `lines` field.  
**Frequency/Recurrence:** Every input that does not end with a line terminator.  
**Severity/Urgency:** Medium. Readers may take the two fields as inconsistent.  
**Confidence:** High. The owner decided that the final segment counts for the longest-line measure.  
**Current State:** The `lines` field excludes the unterminated final segment. The longest-line measure will include it.  

**Evidence Signals:**

- The unterminated final segment counts as a line for the longest-line measure, so `a b c` with no terminator reports 3.
- The existing `lines` counter does not count an unterminated final segment, so `a b c` reports `lines: 0`.

### Pattern 3: definitions-reuse-constraint

**Applies To:** The word rule, the line terminator set and the runtime dependencies.  
**Frequency/Recurrence:** Every run of wordcount.  
**Severity/Urgency:** Medium. A second definition of word or line would make fields disagree.  
**Confidence:** High. The owner requires reuse of SPEC-0001 to SPEC-0005 and no new runtime dependency.  
**Current State:** The word rule and the line terminator set exist in the approved specs. The runtime dependency list is empty.  

**Evidence Signals:**

- The change must reuse the word definition and the line terminator set from SPEC-0001 to SPEC-0005.
- The change adds no third-party runtime dependency.

### Pattern 4: output-contract-stability

**Applies To:** The output line, the README and the existing tests.  
**Frequency/Recurrence:** Every run of wordcount, and every test of the output line.  
**Severity/Urgency:** Medium. A wrong label, wrong position or changed field would break parsers and tests.  
**Confidence:** High. The owner fixed the label and the position.  
**Current State:** The output line has three fields. The README and the tests assert that three-field line.  

**Evidence Signals:**

- The new field uses the label `longest_line_words: N` and comes last, so the line reads `words: W characters: C lines: L longest_line_words: N`.
- The existing fields and their meaning must stay stable for both `wordcount PATH` and `wordcount -`.
- The README and the existing tests assert the three-field output line, so they no longer match the new output.

## Pattern Dependency Graph

The missing longest-line metric is the root pattern. The final-segment rule, the definition reuse and the output contract all constrain how that metric behaves. The final-segment rule differs from the existing `lines` rule, so the documentation must explain the difference. The new field changes the output line, so the README and the tests that assert the three-field line become stale.
